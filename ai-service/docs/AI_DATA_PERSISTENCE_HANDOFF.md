# AI/Data Persistence Handoff

This document defines how AI-service outputs should be persisted into the
`ai_data` SQL Server schema.

Scope: AI/Data owns the schema, seed data, mapping rules, feature fields,
evaluation data, and model metadata. Backend/business services own users,
auth, sessions, employer workflows, and production orchestration.

## P0 Decision

For P0, AI-service does not write production SQL Server records directly.
It returns structured JSON. The service responsible for durable workflow state
persists that JSON into `ai_data` using this mapping.

If AI-service later writes SQL Server directly, add a dedicated repository or
data-access layer. Do not mix SQL writes into parsing, scoring, analysis, or
suggestion services.

## Shared Identifiers

- `user_id`: external business user id, nullable for samples/evaluation.
- `conversation_id`: external chat/session id, nullable for batch jobs.
- `cv_profile_id`: AI/Data id for one parsed CV snapshot.
- `job_id`: AI/Data id for one normalized JD snapshot.
- `match_run_id`: AI/Data id for one scoring result.
- `analysis_id`: AI/Data id for one job-fit analysis result.
- `suggestion_run_id`: AI/Data id for one CV suggestion result.

IDs can be generated by the writer service. If the writer passes ids back to
AI-service, the AI-service can include them in follow-up analysis requests.

## Persistence Order

1. Store uploaded CV metadata in `raw_cv_documents`.
2. Store parsed CV snapshot in `cv_profiles`.
3. Store raw job crawl/fetch metadata in `crawl_runs` and `raw_job_postings`.
4. Store normalized JD snapshot in `job_posts_normalized`.
5. Store extracted CV/JD entities in `entities`.
6. Store ESCO mapping results in `entity_concept_links`.
7. Store feature vector summary in `cv_job_features`.
8. Store ranking/scoring output in `match_runs`.
9. Store detailed analysis in `job_fit_analyses` and `job_fit_gap_items`.
10. Store suggestions in `cv_suggestions` and `cv_suggestion_items`.
11. Store citations and safety flags in `evidence_refs` and `guardrail_flags`.
12. Store evaluation labels in `labeled_cv_jd_pairs`, `labeled_entities`, or
    `labeled_intents` only when a label source is clear.
13. Store embedding prep in `text_chunks` and `embeddings` when benchmarking.

## Endpoint Mapping

### `POST /api/parse-cv`

Persist:

- `raw_cv_documents`: upload metadata, hashes, sanitized preview/json.
- `cv_profiles`: full parsed profile JSON and structured fields.
- `entities`: extracted skills, occupation/title, education keywords.
- `entity_concept_links`: ESCO URI, preferred label, type, ISCO group.

Do not persist `fileBase64`. Do not store raw email/phone; store hashes or
redacted values only.

### `POST /api/scrape-jd`

Persist:

- `crawl_runs`: source, query, status, count, crawler version.
- `raw_job_postings`: source URL, external id, raw text/payload hash.
- `job_posts_normalized`: normalized title, company, salary, skills, JD text.
- `entities` and `entity_concept_links`: JD skills and occupation mapping.

Use `source + external_id` and `source_url_hash` for deduplication.

### `POST /api/match-cv-jd` and `POST /api/recommend-jobs`

Persist:

- `cv_job_features`: feature scores, matched/missing skills, model revision.
- `match_runs`: score, rank, summary, full response payload.

Store scores in SQL as `0..1`. API responses can still present `0..100`.

### `POST /api/analyze-job-fit`

Persist:

- `job_fit_analyses`: overall score, fit label, summary, full response JSON.
- `job_fit_gap_items`: each matched/gap/partial item.
- `evidence_refs`: CV/JD excerpts used for each claim.
- `guardrail_flags`: unsafe or unverified claims.

Every high-impact recommendation should have evidence from CV, JD, or both.

### `POST /api/cv-suggestions`

Persist:

- `cv_suggestions`: one suggestion run.
- `cv_suggestion_items`: individual edits/rewrite/add-if-true suggestions.
- `evidence_refs`: source evidence for why the suggestion exists.
- `guardrail_flags`: for example `requires_verified_experience`.

Do not generate or persist invented experience. Missing skills should become
`add_if_true` or `learning_gap` style suggestions, not verified claims.

## Minimal Writer Contract

```json
{
  "user_id": "sample-user-001",
  "conversation_id": "sample-conversation-001",
  "cv_profile_id": "uuid-or-null-before-write",
  "job_id": "uuid-or-null-before-write",
  "source_endpoint": "/api/analyze-job-fit",
  "request_snapshot": {},
  "response_snapshot": {},
  "model_name": "rule-based-gap-analyzer",
  "model_revision": "rule-based-gap-v1",
  "created_at": "2026-08-22T00:00:00Z"
}
```

The writer can persist this snapshot into the mapped tables and return the
created ids to the caller.

## Phase 7 Readiness

Phase 6.5 is ready for Phase 7 when:

- Schema check passes.
- ESCO seed has at least the starter concepts.
- Sample persistence seed creates one complete CV/JD/match/analysis/suggestion
  flow.
- Smoke test passes.
- The team agrees whether Backend or a future AI worker is the production
  writer.
